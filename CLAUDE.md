## Coin Price Display Rule
* **Mandatory Action:** Any feature that displays a coin's USD price MUST format it through `frontend/frontend/state/coin_state.py::_fmt_usd` (or a helper that itself calls it, e.g. `_price_display_with_fallback`) — never a fresh ad hoc `f"${value:.2f}"`/fixed-decimal string built directly at the display site.
* **Why:** A fixed decimal count always eventually rounds a real, nonzero price down to "$0.00" once a coin is cheap enough — confirmed live twice (once at a fixed 2 decimals for sub-cent coins, again later at a fixed 8 decimals for even-smaller micro-cap tokens). `_fmt_usd` dynamically extends precision (in steps, capped at 24 decimals) until the formatted string ends on a real, non-zero digit, whatever the coin's actual magnitude — $1+ prices still get a plain 2 decimals. Bypassing it for a new feature reopens the exact bug this rule exists to close.
* **How to apply:** Every existing `price_display` field (homepage table, coin detail's big price header, Markets section pair rows, the header search dropdown) already goes through this one function, so this rule is already satisfied everywhere prices show up today — it only needs active attention when *adding* a new place a price gets rendered.

### 🔧 Performance fix: site-wide slowness — SPA routing was not the cause (2026-09-26 session, later same day)
User-reported: clicking buttons, switching pages, and searching all feel slow to finish. Asked whether this is because the app is a single-page app, and requested switching to full browser-reload navigation instead.

**Confirmed by direct timing: it was NOT an SPA-routing problem, and switching to full page reloads would not have helped** (would likely have made it worse — the same expensive work below would still re-run on every fresh page load, plus a full asset re-download and websocket reconnect on top). Reflex's `on_load`/state model doesn't distinguish client-side vs. full-reload navigation for this cost — every `/coin/[symbol]` or `/` visit runs the exact same `on_load` events either way. User confirmed proceeding with the real fix instead of the requested (but wrong-diagnosis) full-reload change.

**Two real, measured causes found, both now fixed:**
1. **`CoinState.load_coins` re-fetched and rebuilt the entire ~8,193-coin universe (eager-loading categories + contracts for every single one) on *every* navigation** — home→coin, coin→home, and coin→coin all share this one `on_load` event. Directly timed: **~2.1 seconds of blocking server time** per call. **Fix**: `load_coins` now skips this entire rebuild whenever `self.all_coins` is already populated (i.e., after the first page visit in a session) — per-page resets (About-section collapse, Markets tab/page) still always run. A brand-new browser session still pays the cost once; every navigation after that is instant.
2. **The bigger cause**: `CoinState.all_coins` — the single state var holding all ~8,193 coins — was **wholly reassigned** by nearly a dozen different handlers (`sync_visible_page` after every category/chain/search/pagination click, `detail_sync_loop`'s 60s tick, `live_sync_loop`'s 60s tick, and all five of a coin page's one-shot background refreshers: social posts, description, business summary, market pairs, TradingView symbol). Directly measured: **the serialized `all_coins` payload is ~31.8 MB**. Every one of those reassignments — even when only 1–100 coins actually changed — re-serialized and re-sent this entire ~32 MB blob over the websocket, and the client had to re-parse and re-render it on every single interaction. This was almost certainly the dominant cost behind "every click feels slow," an order of magnitude bigger than either the artificial 250ms skeleton-visibility delays (`asyncio.sleep(0.25)`, one in each of `set_category`/`set_chain`/`toggle_search`/`set_search_query`/`next_page`/`prev_page`/`go_to_page`/`set_page_size` — an earlier session's deliberate choice, left as-is this session) or the ~1.2s live CMC re-sync `sync_visible_page` does for a 100-coin page.

**Fix #2, applied** (`coin_state.py`): new `CoinState.coin_overrides: dict[int, dict]` — a small dict keyed by `cmc_id`, holding *only* whichever fields a background refresh actually touched for that one coin. `all_coins` itself is now written to exactly once per session (`load_coins`'s initial full load) and never reassigned again — every previously-reassigning handler (`_apply_updates`, `refresh_social_posts`, `refresh_coin_description`, `refresh_business_summary`, `refresh_market_pairs`, `refresh_tradingview_dex_symbol`) now merges its patch into `coin_overrides` instead, which stays orders of magnitude smaller (bounded by however many distinct coins a session has actually touched, not the full universe). New `_row_with_overrides(row)`/`_merged_row(cmc_id)` helpers do the read-side merge — `filtered_coins` (and therefore `paged_coins`/`sorted_paged_coins`, everything the homepage table renders), `selected_coin` (everything a coin's own page renders), and `live_sync_loop`'s top-100 selection all merge overrides in *before* filtering/sorting/paginating, so live-synced data still shows up correctly and immediately — only the *output* of those computed vars (small, already paginated/selected) crosses the websocket now, never the full 8,193-row list again after the first load.

**Verified live (Playwright, real end-to-end page visits, after this fix)**: homepage pagination still correctly advances (page 2 → ranks 101+), search still correctly ranks results by true global market-cap position (Dogecoin → rank 12 among 8 "dogecoin"-named results), and Ethereum's coin-detail page still shows its real price, real chart (`BINANCE:ETHUSDT`), and its Markets/AI-Summarizations/About sections — confirming the `coin_overrides` merge didn't regress any of the business-summary/market-pairs/chart-symbol machinery built earlier this session.

40. **`telegram_listener.py` isn't started automatically, and it must run as exactly ONE process.** Start it by hand from the repo root (`python -m app.services.telegram_listener > telegram_listener.log 2>&1`) after a restart; it stops when its terminal/session ends. `telegram_session.session` is SQLite, so two overlapping listeners crash with `database is locked` (happened 2026-09-30 after a few careless restarts). **When stopping/restarting it, find the process with a case-insensitive match** (`ps aux | grep -i telegram_listener`): the interpreter shows up as `Python` (capital P) on macOS, so `pgrep -f "python -m ..."` misses it and only matches the shell wrapper, which leaves the real listener running. Kill every matching PID, confirm none remain, then start one. If always-on is wanted, run it under a process manager (launchd/`pm2`); not set up yet. **Also a latent risk**: the repo lives in `~/Documents`, and macOS `fileproviderd` (iCloud/File Provider sync) keeps `telegram_session.session` open for write; it may cause sporadic lock errors on a long-running listener. If `database is locked` recurs with only one listener running, move the session file outside `~/Documents` (change `SESSION_PATH` in `telegram_pipeline.py` and `scripts/telegram_login.py` to match).
